## 2. 推理性能

| 场景 | 分辨率 / 步数 | 耗时 | 峰值显存 |
|---|---|---|---|
| 文生图 | 512×512 / 8 步 | 1.8 s | — |
| 文生图 | 1024×1024 / 20 步 | **10.9 s**（0.54 s/步） | 36.8 GiB |
| 文生图 | 1024×1024 / 25 步 | 13.9 s | 36.8 GiB |
| 文生图 | 2048×2048 / 40 步（分块 VAE） | **115.3 s**（2.88 s/步） | 32.5 GiB |
| 图像编辑 | 1 参考图 → 832×1248 / 30 步 | 21.3 s | 38.8 GiB |
| 图像编辑 | 1 参考图 → 832×1248 / 35 步 | 23.7~24.5 s | — |
| 图像编辑 | 2 参考图（锚定） / 35 步 | 28.2~28.4 s | — |
| 图像编辑 | `output_resolution=1280` → 1056×1568 / 35 步 | 50.8 s | — |

关系：耗时 ≈ 步数 × 序列长度；2048² 的像素是 1024² 的 4 倍，时间是 10.6 倍。

## 3. 两条硬约束

### 3.1 2048² 必须开分块 VAE 解码

不开 `QWEN_TILE_VAE=1` 时，DiT 采样能过，**崩在最后的 VAE 上采样层**：

```
torch.OutOfMemoryError: Tried to allocate 4.50 GiB.
GPU 0 has a total capacity of 47.37 GiB of which 2.30 GiB is free.
  autoencoder_kl_qwenimage21.py:1318  out = self.decoder(...) → self.resampler
```

原因：DiT 30 GiB 常驻 + 2K 的 VAE 解码特征缓存，同时挤在 47 GiB 里。
`serve.sh` 已默认带上 `QWEN_TILE_VAE=1` 与 `PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True`。

### 3.2 编辑输出尺寸被钉在 1MP 档位

给 1696×2528 的参考图，**不传 `width`/`height` 时输出 832×1248**；
显式传 `width=1696&height=2528` 仍输出 832×1248（日志提示 ignored input width/height）。
真正的旋钮是管线参数 **`output_resolution`**（默认 1024），已透出到接口：

| output_resolution | 实际输出 | 耗时 | 保真度 |
|---|---|---|---|
| 1024（默认） | 832×1248 | 24.5 s | 基准 |
| 1280 | 1056×1568 | 50.8 s | **更差**（人脸漂移 0.203 vs 0.172） |

**提高分辨率只让耗时翻倍，不改善一致性。**

## 3.2 输出尺寸的真实规则（2026-09-26 实测 + 读 diffusers 源码）

`QwenImage21Pipeline.__call__` 源码第 118-124 行：

```python
calculated_width, calculated_height, _ = calculate_dimensions(
    output_resolution * output_resolution,      # 像素预算 = 分辨率的平方
    image[-1].size[0] / image[-1].size[1])      # 比例 = 参考图
height = height or calculated_height
width  = width  or calculated_width             # 显式传了就优先
```

所以 **`output_resolution` 是"像素预算"，参考图给比例，显式 `width`/`height` 优先级最高**。

### 文生图

| 参数 | 实际输出 |
|---|---|
| `1024×1024` | 1024×1024 |
| `2048×2048` | 2048×2048（**必须开分块 VAE**） |
| `aspect_ratio=2:3` | 1696×2528 |

### 编辑（有参考图）

| 参考图 | 参数 | 实际输出 |
|---|---|---|
| 1024×1024 | 不传 | 1024×1024 |
| 768×1024 | 不传 | **896×1184**（比例跟随参考图，预算 = 1024²） |
| 1024×768 | 不传 | **1184×896** |
| 768×1024 | `output_resolution=1280` | 1120×1472 |
| 768×1024 | `output_resolution=512` | 448×576 |
| 768×1024 | `width=1088&height=1440` | 1088×1440（**显式尺寸生效**） |

**`width`/`height` 是编辑模式唯一的分辨率杠杆**。服务端为此加了 `explicit_size` 标记：
显式给了就传给管线，没给就丢掉让管线按"预算 + 参考图比例"推导。

## 3.3 编辑模式的显存边界（关键限制）

48G 卡、权重常驻 30.2G、分块 VAE 开启时，**编辑模式上限约 1.92MP**：

| 目标尺寸 | MP | 结果 |
|---|---|---|
| 1088×1440 | 1.57 | ✅ |
| 1152×1536 | 1.77 | ✅ |
| **1184×1600** | **1.89** | ✅ **上限附近** |
| 1280×1696 | 2.17 | ❌ CUDA OOM |
| 1696×2528（原生 2K） | 4.29 | ❌ CUDA OOM |

对比：**文生图 2048²（4.19MP）能跑**（峰值 32.5G）。编辑还要多编码一张参考图
（条件 latent + 图像 token 一起进序列），曲线陡得多，所以两条路线上限完全不同。
想要 2K 编辑只能开 `QWEN_OFFLOAD=model`。

## 3.4 两个会让人误判的坑

1. **必须用 `serve.sh` 起服务，别用裸 `python service/server.py`** —— `serve.sh` 会设
   `QWEN_TILE_VAE=1`，裸起就漏了，2048² 直接 OOM；崩完还会留下碎片，后面请求全被误伤
   （实测：裸起后 2048² 文生图必崩、编辑 1184×1600 也被预检误拦）。
2. **`QWEN_TILE_VAE` 在 `qwen_env.sh` 里的默认值曾被写成 0**，造成"文档说要开、实际一直没开"。
   现在两处都默认 1。

## 3.5 显存预检公式（按实测校准，分模式）

```
临时量 = max(线性项, 二次项) + 步数修正
  线性项 = 8.0 × (像素 / 2048²)
  二次项 = 系数 × MP²     编辑 3.65 G/MP²，文生图 0.5 G/MP²
```

**分模式是必须的**：用编辑的系数去算文生图，2048² 会被估成 64.2G → 误拦一个本来能跑的请求。

| 尺寸 | 模式 | 估算 | 实测 | 预检 |
|---|---|---|---|---|
| 1184×1600 | edit | 13.1G | ✅ | 放行 ✓ |
| 1280×1696 | edit | 17.2G | ❌ OOM | 拦住 ✓ |
| 2048×2048 | t2i | 8.8G | ✅ 峰值 32.5G | 放行 ✓ |

校验：`python tools/check_vram_formula.py`（不需要 GPU）。

## 3.6 多参考图（官方 multi-subject composition）实测

官方 README 把"一次喂多张参考图"归在 **Image Editing → Multiple Reference Images**，
用途是 multi-subject composition，示例是"六张单人头像合成一张合影"、
"人+外套+鞋+包+帽 拼一套穿搭"。本机实测：

| 参考图组合（顺序） | 参数 | 输出 | 耗时 |
|---|---|---|---|
| A(768×1024) + B(1024×1024) | 不传尺寸 | **1024×1024** | 8.2s |
| B(1024×1024) + A(768×1024) | 不传尺寸 | **896×1184** | 8.3s |
| A 单张 | 不传尺寸 | 896×1184 | 6.6s |
| B 单张 | 不传尺寸 | 1024×1024 | 6.3s |
| A + B | `width=1184&height=1600` | 1184×1600 | 15.9s |

**关键结论：默认输出比例由最后一张参考图决定**（管线内部用 `image[-1]`，
与 `calculate_dimensions(..., image[-1].size[0]/image[-1].size[1])` 一致）。
所以顺序是有语义的 —— UI 里为此加了"最后一张决定比例"的提示。

### "两个人拥抱"应该用哪个接口

**用编辑接口（`/v1/images/edits`）+ 两张参考图。** 理由：

1. 官方 README 的 *Image Editing (Multiple Reference Images)* 就是这个用法，
   `image=[img1, img2, img3]` + prompt 描述场景；
2. 只传文字（文生图）也能画出"两个人在拥抱"，但两个人长什么样完全由文字决定，
   不受你的图控制 —— 没有参考图，模型看不到那两个人；
3. 只给一张参考图 → 模型只"认识"一个人，另一个只能靠文字编，长相不可控；
4. 底层是**同一个管线**（`QwenImage21Pipeline`）：传 `image` 即条件生成，不传即纯文本生成。
   "编辑"并不是只能改一张图，它是统一的条件生成接口。

实测样例（两张参考图 → 拥抱，1184×1600 / 14 步 / 22.1s / 每步 1.35s）：
`test-data/remote_outputs/hug_two_people.png`，两个人的发色与服装分别对应两张参考图。

## 3.7 「文生图」和「图像编辑」到底是不是两件事（2026-09-26 验证）

**底层是一件事**：只有一个 `QwenImage21Pipeline`，参数里 `image` 就在同一个签名中
（`prompt, image, height, width, num_inference_steps, …`）。传 `image` = 条件生成，
不传 = 纯文本生成。官方 README 也把多参考图归在 *Image Editing* 下，而不是另起一个模型。

**但有三处行为真的分叉，判据是"有没有参考图"，不是"用户选了哪个 Tab"**：

| 验证项 | 无参考图 | 有参考图 |
|---|---|---|
| 不传尺寸的默认输出 | **2048×2048**（官方默认 2K） | **跟随参考图比例**（768×1024 + budget 1024 → 896×1184） |
| 同一尺寸 2048² | ✅ 能跑（峰值 32.5G） | ❌ OOM（条件图 latent + 图像 token 占显存） |
| 显存曲线（二次项系数） | 0.5 G/MP²（平缓） | 3.65 G/MP²（陡） |
| 参考图缩放 | — | `output_resolution` 同时用于缩放参考图 |

**推论**：UI 上分两个 Tab 只是"命名"和"默认值引导"，模型层面没有两条路。
真正的开关是"参考图框里有没有图"。服务端已按这个判据统一（见下方"单入口"）。

### 单入口实测（同一个端点，`image` 可选）

```
JSON，无图，不传尺寸                 -> 2048x2048
JSON，带 1 张 image_b64              -> 896x1184
multipart，无图                      -> 2048x2048
multipart，1 张图                    -> 896x1184
multipart，2 张图 + width/height      -> 1184x1600
multipart，无图 + aspect_ratio=16:9   -> 2752x1536
/v1/images/edits（旧端点）            -> 与上面完全等价（转发到同一实现）
```

### 尺寸推导公式（已与官方源码逐字对齐）

`pipeline_qwenimage21.py` L148-157：

```python
def calculate_dimensions(target_area, ratio):
    width  = math.sqrt(target_area * ratio)
    height = width / ratio              # 用未取整的 width
    width  = round(width / 32) * 32     # round 到 32（不是 floor 16）
    height = round(height / 32) * 32
```

我第一版把取整写成 `floor(.../16)*16`、并拿取整后的宽反算高，7 个实测里 6 个对不上；
改成上面的实现后 **7/7 全对**。校验脚本：`python tools/check_size_formula.py`。

---

四步链，每步把上一步输出当输入，同 seed 22，35 步：

| 步骤 | 耗时 | 相对上一步 SSIM | 人脸漂移（累计 vs 原图） |
|---|---|---|---|
| 1 姿势 | 23.7 s | 0.269 | **0.180** |
| 2 表情 | 23.4 s | 0.616 | 0.223 |
| 3 手 | 23.6 s | 0.846 | 0.215 |
| 4 机位 | 23.9 s | 0.892 | 0.211 |

四条结论：

1. **不存在"只改某处"**：第 1 步只要求改姿势，人脸区域漂移 0.180 ≈ 整图漂移 0.177。
   四步后与输入的 SSIM 只剩 **0.138**——脸已不是原来那张脸。
2. **提示词措辞无效**：对照组 A（自然长句 `Keep the same character, same face...`）与
   B（`KEEP:` / `CHANGE:` 清单式）逐步数值几乎逐位重合（0.2691 vs 0.2501、0.6163 vs 0.6064…）。
3. **原图锚定反而更差**：`image=[当前图, 原图]` 时人脸漂移 0.172 → 0.179，单张耗时 +4 s
   （第二张参考图的 prefix KV 缓存额外吃约 8 GiB）。
4. **漂移单调但累加**，链越长越像另一个人。

## 5. 身份补偿（`service/face_fix.py`）

做法：把源图人脸按羽化椭圆贴回编辑帧。数值是相对原始输入的人脸区域 MAD。

| 编辑产物 | 补偿前 | 补偿后 | 改善 |
|---|---|---|---|
| 四步链 A 终帧 | 0.2702 | 0.2366 | −0.0336 |
| 四步链 B 终帧 | 0.2686 | 0.2340 | −0.0346 |
| 姿势步（单参考图） | 0.1722 | 0.1424 | −0.0298 |
| 姿势步（原图锚定） | 0.1794 | 0.1503 | −0.0291 |
| 姿势阶梯 L1 | 0.1934 | 0.1496 | −0.0438 |
| 蹲姿 seed22 | 0.1659 | 0.1354 | −0.0305 |
| 蹲姿 v2 | 0.1620 | 0.1289 | −0.0331 |

**自动定位人脸不可行**，三种方案实测全败（留档在 `qwen_skin_probe.py` / `qwen_template_probe.py`）：

| 方案 | 失败方式 |
|---|---|
| Haar 级联 | 把整块上半身 `(174,0,731,552)`、背景花丛 `(885,348,1018,492)` 当脸 |
| 归一化模板匹配 | 背景（书架/蓝墙）随姿势全变，最高分仅 0.44~0.63，位置偏到眼睛下方 |
| 肤色 HSV 连通域 | 整图蓝色调，掩膜几乎为空；偶尔的候选是手臂 |

因此实现采用**固定位置贴回 + 置信度闸门**：只在头部位移小的帧上执行。
`qwen_facefix_sanity.py` 是自检脚本——贴回后中心区域应与源图逐像素相等，
第一版正是靠它发现"贴错位置反而更差"（误差 70 vs 编辑图本身 51）。

## 7. 指令响应矩阵（`tools/matrix_test.py` + `tools/matrix_report.py`）

方法：每条指令配一个**空指令基线**（"Return the image unchanged"），逐像素对比。
关键前提：**基线本身与输入图的 MAD 就是 0.104** —— 模型即使被要求什么都别改，也会重画整张图。
所以判断"指令有没有生效"不能看有没有改动，要看**目标区域的改动是否显著超过基线的重绘幅度**。

| case | 分组 | target_d | rest_d | 与基线总差 | 判定 | 目视复核 |
|---|---|---|---|---|---|---|
| B0_baseline | 基线 | 0 | 0 | 0 | — | 与输入几乎一样，但仍有 0.10 的整图重绘 |
| P1_pose_stand | 姿势 | 0.2051 | 0.0922 | 0.1733 | 有响应 | ✅ 真的站起来，房间保留 |
| P2_pose_arms_up | 姿势 | 0.1995 | 0.0557 | 0.1396 | 强响应 | ✅ 双臂举过头顶 |
| C1_cloth_red | 服装 | 0.1984 | 0.0875 | 0.1243 | 有响应 | ✅ 裙子变深红 |
| C2_cloth_remove_sleeves | 服装 | 0.0395 | 0.0323 | 0.1064 | 不明 | ✅ 袖子消失（局部小改动被整图重绘掩盖） |
| B1_bg_beach | 背景 | 0.5323 | 0.4301 | 0.5041 | 不明 | ✅ 房间变沙滩正午 |
| B2_bg_wall_white | 背景 | 0.6649 | 0.4782 | 0.5612 | 强响应 | ✅ 换白墙（整体过曝，人物细节牺牲） |
| O1_add_cat | 物体 | 0.0217 | 0.0198 | 0.1053 | 不明 | ✅ 左侧地面出现灰猫 |
| O2_remove_globe | 物体 | 0.0295 | 0.0245 | 0.1039 | 不明 | ❌ 地球仪未删除 |
| E1_expression_smile | 表情 | 0.0218 | 0.0349 | 0.1067 | 重绘而非执行 | ❌ 表情无变化 |
| E2_expression_sad | 表情 | 0.0209 | 0.0306 | 0.1047 | 重绘而非执行 | ❌ 表情无变化，且与 E1 近乎相同 |

| 对比 | MAD |
|---|---|
| 相反表情指令（笑 vs 哭） | **0.013** ← 几乎相同 |
| 两种不同背景指令 | 0.0876 |
| 两种不同姿势指令 | 0.1602 |

### 结论

- **可靠**：背景替换、服装换色/改款式、整体画风、姿势改造、头部朝向、头发颜色、多指令叠加
- **不可靠**：表情（几乎完全不响应）、删除画面中的物体（失败）、加小物体（能加但很飘）、
  照片写实化（只是提亮抹平）
- **规律**：模型响应**大范围、低频率、全局性**的改动，对**局部、细小、语义级**的改动
  一律退化成"再来一次整图重绘"，而重绘结果与基线几乎相同。

产物：`test-data/matrix/`，报告：`reports/matrix-report.html`

## 7.1 补充案例：局部纹理替换（裙子花纹 → 贝壳）

矩阵结论"局部改动不响应"需要收窄。把连衣裙上的碎花图案换成贝壳，**三条不同措辞全部成功**：

| 版本 | 裙子区差异（vs 输入） | 结果 |
|---|---|---|
| S0 基线（原样返回） | 0.0801 | 纹样被抹平，锐度 3294 → 882 |
| S1_shells | 0.1075 | ✅ 贝壳出来了，但配色偏到米白 |
| **S2_shells_strict** | **0.1010** | ✅ **最佳**：蓝紫贝壳，最贴近原配色 |
| S3_shell_print_only | 0.1039 | ✅ 贝壳出来，配色偏浅 |

**修正后的分类**：

| 类型 | 例子 | 响应 |
|---|---|---|
| 局部**纹理/图案**替换（密集重复、大面积铺开） | 碎花 → 贝壳 | ✅ 执行 |
| 局部**语义**改动（稀疏、需要定位） | 表情、删地球仪、加猫 | ❌ 不响应或极飘 |
| 全局改动 | 背景、画风、服装主色 | ✅ 稳定 |

**方法学教训**：这类改动的全图指标完全失效（基线 0.0679 vs 贝壳版 0.0739~0.0768），
只有把差异限制在目标区域才能看出来（0.0801 → 0.1010~0.1075，高出 26%~34%）。
局部纹理改动的验收必须"限区域量化 + 目视"，不能看全图数字。

详情见 [CASE-dress-shell.md](CASE-dress-shell.md)。

## 8. 姿势与失效边界（`qwen_pose_test.py` / `qwen_nsfw_test.py`）

| 测试 | 结果 |
|---|---|
| 蹲姿（2 组提示词 × 3 seed） | 6 张里 2 张可用；极端姿势下膝盖位置错乱、腿长短不一 |
| 姿势阶梯 L1（双臂后撑、大腿打开） | ✅ 最好的一版，结构合理 |
| L3（跪蹲前倾、双手撑地） | ✅ 可用，脚被裁出画面，头身比偏 Q |
| L2（强调裙摆铺开） | ❌ 模型把裙子整个删掉，姿势退化成坐着 |
| L4（低机位、双手扶膝） | ❌ 低机位指令被完全忽略，内层服装被删 |

**失效模式**：涉及"裙摆与大腿的空间交叠"这类它算不明白的遮挡关系时，
模型的选择是**删掉裙子**；四肢互相遮挡时会**数错腿**。这是 7B 单流 DiT 的容量限制。

**对比**：同一模型走**文生图**路线时结构稳定得多（河边钓鱼 1024×1024 一次通过），
因为姿势是"生成"出来的，模型可以自选最舒服的构图，而不是从参考图硬改。

产物：`test-data/poseA_*`、`test-data/nsfw_L*`、`test-data/poseB_*`

## 9. 给上游对接的建议（结论汇总）

1. **优先用文生图直出，不要用编辑链硬拧姿势**——两者稳定性差距很大。
2. **必须多步时，链越短越好**，并且把大改动（姿势）放第一步。
3. **人脸一致性只能靠链路之外补**：`face_fix.py` 固定位置贴回，或用报告里的手动对齐工具。
4. **提示词别写复杂的"只改 A 保留 B"**——实测措辞对保持率零影响，不如把指令拆成多步。
5. **别指望表情/微表情控制**，这个模型没有这个能力；需要就用别的模型或 LoRA。
6. **2K 出图记得分块 VAE**；编辑接口的输出尺寸想要更大只能改 `output_resolution`（且不划算）。
7. **批量出图用 `/v1/jobs` 异步接口**，单张 24 s，同步等太慢；单卡串行，队列深度看 `/health`。
